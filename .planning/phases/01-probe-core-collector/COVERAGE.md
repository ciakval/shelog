# Phase 1: Shelly Cloud Control API coverage

**Written:** 2026-10-31 by the phase planner (API coverage checkpoint).
**Re-validated by:** plan 01-07, against one live probe run of 2026-11-01 (evidence in `docs/shelly-api.md`; fixtures under `tests/fixtures/shelly/`). Like every `.planning/` file, this table holds device names and aggregate or pseudonymized values only; plan 01-03's real-id and key scans cover it.
**Sources:** shelly-api-docs.shelly.cloud `cloud-control-api/` (Getting Started), `communication` (v1, marked deprecated), `communication-v2` (v2.0-beta), `real-time-events`; 01-RESEARCH.md; live discovery run of 2026-10-31 (CONTEXT D-06..D-08).

shelog is a read-only logger (REQUIREMENTS "Out of Scope": device control / settings changes). Every control capability is therefore OPT-OUT. All requests share the account-wide 1 request/second limit.

| capability | decision | reason |
|---|---|---|
| v1 `POST /device/all_status` (all devices of the account in one call, `auth_key` in the form body) | INTEGRATE | Primary poll path (D-06): one request per cycle returns all 7 devices, each with `_updated` (the UTC report time for every model, D-07), and the key never enters a URL (D-05). |
| v1 `all_status` with `show_info=true&no_shared=true` (adds `_dev_info`: `id`, `gen`, `code`, `online`; documented on the Real Time Events page) | INTEGRATE | Probe-only step. Observed: `_dev_info` carried `id`, `gen`, `code` and `online` for all 7 devices (all online, all `_sleeping`), matching `devices.toml` models. Used once by `shelog probe` to cross-check each device's model/generation and the cloud `online` flag. The poller does not use it, because the model comes from `devices.toml`. |
| v1 `POST /device/status` (one device per call, `id` + `auth_key`) | OPT-OUT | Marked deprecated by Shelly. Seven devices would need seven requests per cycle under a 1 req/s limit, and `all_status` already returns the same per-device block. |
| v2 `POST /v2/devices/api/get` with `select:["status"]` (1-10 ids, key documented only as a query parameter) | OPT-OUT | Not a runtime path. Observed: `_updated` IS present in the v2 status for every model including Gen1 sleepers, and the key was accepted in the URL query and in the JSON body (not as a form body: HTTP 400, nor as a Bearer header: HTTP 401); unknown ids are silently omitted. Because v1 offers the same data in one call without an id list, the decision stays OPT-OUT; v2 with the key in the JSON body is a viable fallback if v1 starts returning the `endpoint_gone` category. |
| v2 `get` with `select:["settings"]` / `pick` | INTEGRATE | Probe-only step. Observed: the cloud returned `sleep_mode` (12 h for all six Gen1 devices), both thresholds (0.5) and both offsets (0) for sleeping Gen1 units, and a 7200 s `sleep_mode` for the Gen3 (PROBE-05). Read once by `shelog probe` and never polled. |
| v1 `POST /device/settings` (undocumented) | OPT-OUT | Probed once under `--errors`. Observed: the route exists (HTTP 200, `data.device_settings`, one device per call), contrary to the expected 404. Still OPT-OUT: undocumented, one request per device, and v2 already returns the same settings for all devices in one call. |
| v2 `POST /v2/devices/api/set/switch` | OPT-OUT | Device control is out of scope for a read-only logger, and the sensors have no switch. |
| v2 `POST /v2/devices/api/set/cover` | OPT-OUT | Device control is out of scope. |
| v2 `POST /v2/devices/api/set/light` | OPT-OUT | Device control is out of scope. |
| v2 `POST /v2/devices/api/set/groups` | OPT-OUT | Group device control is out of scope. |
| v1 `/device/relay/control`, `/device/relay/roller/control`, `/device/light/control` | OPT-OUT | Device control is out of scope, and these routes are deprecated. |
| v1 `/device/relay/bulk_control`, `/device/light/bulk_control`, `/device/roller/bulk_control` | OPT-OUT | Bulk device control is out of scope. |
| Real Time Events WebSocket (`wss://<host>:6113/shelly/wss/hk_sock`, `Shelly:StatusOnChange`, `Shelly:Online`) | OPT-OUT | Deferred to the v2 backlog (ROB-02). It needs an OAuth access token instead of the auth key, and the DIY client id may be rate-limited. Polling every 60 s with dedup already meets the ~5 min target. |
| Real Time Events `Shelly:CommandRequest` (relay/light/roller commands over the socket) | OPT-OUT | Device control is out of scope. |
| OAuth login + token exchange (`my.shelly.cloud/oauth_login.html`, `/oauth/auth`) | OPT-OUT | Only needed for Real Time Events. The auth key is enough for polling, and OAuth would add an interactive login and token refresh to an unattended service. |
| Statistics / history charts | OPT-OUT | The Cloud Control API documents no history endpoint. A cloud-stats backfill importer is v2 backlog item ROB-03. |
| Integrator API (cloud-to-cloud, many accounts) | OPT-OUT | Meant for third-party integrators. shelog reads one owner account. |
| Account rate limit (1 request/second) | INTEGRATE | `RateGuard` keeps at least 1.1 s between any two requests (poller and probe), with no way to skip it and no deliberate bursts. HTTP 429 / `Retry-After` and `isok:false` + `max_req` map to `rate_limited` with capped backoff (COLL-01/02). The real throttle envelope is unverified (never provoked live, by decision) and is covered only by `tests/fixtures/shelly/synthetic_rate_limit.json` (plan 01-04); the poller records any real throttle in `poll_log`. Observed instead: a wrong key or a neighbouring regional host both answer HTTP 401 `UNAUTHORIZED` with the same body, so `AUTH_CONFIRMATIONS` stays 2. |
| Server URI relocation and auth-key rotation | INTEGRATE | The host comes from `SHELLY_HOST`. A rejected key becomes a distinct `rejected` auth state, stored in `meta` and logged loudly. A vanished v1 route maps to `endpoint_gone` (COLL-02). Observed: a neighbouring regional host answers a foreign key exactly like a wrong key (HTTP 401, same body), so a moved host is indistinguishable from a rotated key and both surface as `auth`. |
